# Member 5 operations and handoffs

## Database ownership and migration coordination

`backend/migrations` is the ordered SQL migration ledger. The runner holds a PostgreSQL advisory lock, runs each migration transactionally and stores its SHA-256. Previously applied files must not be edited; add a new migration. Review teammates' changes for `(room_id, child_id)` foreign keys, indexes, cutoff rules and locks. The initial migration supplies identities, topics, rooms, participants, rounds, scores/results, consent, audio tracks/segments/manifests, transcripts, jobs, outbox and deletion tombstones. It does not implement teammates' authentication or room state machines.

Each audio track identifies its room, round, participant and recording through composite foreign keys. The trusted media adapter must derive those IDs from server authentication and track bindings, not request bodies. Consent references cannot cross rooms; the feature service must verify consent is current before accepting or playing media. Withdraw consent and call `requestDeletion` in one transaction. Default retention is a **provisional 30 days**, not a legal/product policy; feature owners must set each recording's `retention_until` explicitly. `RETENTION_DAYS` is exposed for that integration.

Only canonical server-relative timestamps may enter storage. The database rejects segments beyond the recording cutoff and edits after sealing/deletion. The shared manifest validator rejects gaps, overlaps and wrong sequence. M3 must validate all tracks before inserting a manifest and marking a recording complete; no API accepts client manifests in this foundation. M4 owns transcription generation, language confidence and scoring use. Transcript indexes are provided, but no language support is claimed.

For rollback: drain all writers, create and independently verify a backup, run the previous application against the newer additive schema where compatible. Prefer forward fixes. A destructive schema rollback requires `ALLOW_DESTRUCTIVE_ROLLBACK=yes npm run db:migrate -- down` and removes the most recent migration only. The foundation down migration deletes all feature data and is appropriate only for disposable development or a verified recovery plan. Never run it as an automatic deployment rollback.

## Durable workers and outbox

Insert domain state plus `outbox` in the same database transaction. The dispatcher transfers events to `jobs` and marks delivery atomically. Dedupe keys are globally unique and must include event identity/version; reuse with a changed payload fails. Delivery is at least once. A PostgreSQL claim uses `FOR UPDATE SKIP LOCKED`, database-clock leases, increasing fencing tokens and bounded retries. Every database side effect must run inside `finishJob`; a worker that loses its lease cannot commit. External effects must be idempotent because a crash can occur after the external operation and before the database commit.

The worker currently handles `storage.retention`, `storage.orphans`, and `storage.delete`; it never consumes unsupported teammates' job kinds. Lease renewal happens every third of the lease duration. A SIGTERM stops new claims and gives the active task up to 25 seconds; unfinished claims expire and are reclaimed. On `FAILED` jobs, inspect the correlated job ID, correct the root cause, then enqueue a new versioned dedupe key under operator control. Do not reset a live fence or lease manually. Test-only clock manipulation is confined to disposable schemas.

Use unique object keys permanently. Staging uploads expire after one day and incomplete multipart uploads are aborted through bucket lifecycle. Completed-prefix objects older than a day with no metadata reference are reconciled into deletion tombstones, in inventory pages of 100. Object-key advisory locks serialize orphan discovery with metadata insertion. Staging-to-completed finalization and checksum/manifest validation belong to M3. A tombstoned key may never be reused. The one-day age is a provisional maximum finalization window.

## Private storage and playback

S3 buckets have no public policy; initialization refuses an existing bucket policy for review. No public bucket routing is exposed by Nginx/Caddy. Use dedicated bucket/credentials for this app. The local single-node MinIO service is for development, not a production HA or capacity claim. It is built from upstream commit `f19c534b9f457773dcd043d977433e1a71525c3b`, with archive checksum verification and Go module verification enabled. Review the chosen upstream version/licensing/security updates before production use.

`signedRead` is an internal primitive, not an unauthenticated route. The future playback endpoint must authenticate membership, check consent and recording status/tombstones, and only then sign a 60-second URL. Existing signed URLs can remain usable until expiry or object deletion; strict immediate revocation needs an authenticated streaming gateway. Configure a reachable HTTPS S3 endpoint for browser signing; the internal Compose hostname `storage` is not a public browser endpoint. Do not expose the storage administrator console publicly.

## Backup, restore and deletion tombstones

1. Put ingress in maintenance mode. Stop new rooms, drain M3's active recording sessions, finish manifests, and stop **all** writers (API, worker, media/recording, transcription). These last services are not supplied yet. A database-only snapshot while media is changing is not a consistent audio backup.
2. Run `MAINTENANCE_ACK=yes bash scripts/backup.sh backups/NEW_NAME`. The destination must be new. It contains `pg_dump -Fc`, canonical object bytes with per-object SHA-256, and tombstones. The manifest is written last, so incomplete object backups fail restoration. Staging is deliberately excluded. Store backups encrypted, access-controlled and off-host.
3. Independently export deletion tombstones frequently: `node --env-file=.env backend/dist/scripts/objects.js export-tombstones NEW_PATH`. Retain the **latest** ledger separately from older backups; an old backup alone cannot prove that later user deletions were honored. This external ledger is an operational requirement, not implemented remote backup automation.
4. Verify backup checksums, then run `bash scripts/restore-db.sh BACKUP_DIRECTORY restore_drill_NAME`. It refuses a production database name and creates a new database; it does not overwrite a database.
5. In a separate recovery environment, configure that restored database and a new private empty bucket. Initialize the bucket. Run `node --env-file=RECOVERY_ENV backend/dist/scripts/objects.js restore BACKUP_DIRECTORY/objects LATEST_TOMBSTONES.json`. This merges tombstones first, purges derived text/manifests, excludes deleted object keys, verifies all object checksums before upload, and queues deletion reconciliation. Do not route traffic if any step fails. Restore targets must be empty; immutable object writes fail on collisions.
6. Start the recovery worker, verify no pending deletion reconciliation, validate restored counts and private reads, then switch traffic through the normal deployment process. Test recovery time/object counts on representative data before setting RPO/RTO.

`bash scripts/verify-db-restore.sh` is a non-destructive PostgreSQL-only drill: it dumps the current dev DB, restores into a newly named temporary DB, compares migration/topic/tombstone counts, then drops only that temporary DB. The S3 integration test separately checks checksum failures and tombstone exclusion. `npm run test:recovery` additionally creates isolated source/restore databases and private buckets, restores a snapshot plus a newer deletion ledger, verifies the erased audio/transcript stay removed, and runs the recovery worker. It cleans up only its own fixture databases/buckets. These are fixture drills, not production disaster recovery certificates.

## Deployment, HTTPS/WSS and media drain

The base Compose stack is a local single-host development stack. For an actual host, set public DNS `ROOM_HOST` and use `docker compose -f docker-compose.yml -f infra/compose.https.yml up -d`. Caddy terminates HTTPS and forwards WebSocket upgrades through Nginx. Ports 80/443 and certificate issuance must be reachable. Use secrets management, separate database service roles, restricted S3 credentials, durable managed storage/backups and capacity tests before production. Do not deploy this starter as a complete debate product.

`infra/compose.turn.yml` packages optional Coturn on a Linux host. Copy `infra/turnserver.conf.example` into ignored `infra/generated/turnserver.conf`, populate a random shared secret, public IP, realm and valid TLS certificate/key. Restrict file access; never commit them. Allow TCP/UDP 3478, TLS 5349 and UDP relay range 49160–49200 at the host firewall. M3 must issue short-lived HMAC TURN credentials after membership authentication; no static TURN passwords belong in the frontend. TURN-only acceptance must use `iceTransportPolicy: relay` and assert the selected candidate is relay. `npm run test:turn` verifies a separate ephemeral local authenticated TCP TURN configuration; public DNS, TLS and firewall traversal have not been deployed or verified.

M3 must provide the SFU/recording image, health endpoint, media ports, persistent staging contract and drain hook. They are intentionally not invented here. Deployment order: database/storage → migrations and bucket initialization → workers → API → web/edge → media only after its owner supplies the integration. Shutdown order: stop new room admission → drain active media with an explicit bounded deadline → finalize or mark recordings failed → stop workers/API. On deadline loss, preserve incomplete status; do not score incomplete audio as successful. No automatic full media drain is claimed.

## Network and proxy build requirements

npm needs `registry.npmjs.org`; image pulls need Docker registry/CDN access; the pinned storage source uses `codeload.github.com`, `proxy.golang.org`, `sum.golang.org` and Go proxy redirects at `storage.googleapis.com`. Playwright uses `cdn.playwright.dev` and its browser CDN destinations. Preserve TLS/checksum verification.

Behind a managed HTTPS proxy, Docker build containers may need explicit proxy arguments, a resolvable proxy hostname and an extra trusted CA. Dockerfiles accept the optional BuildKit secret `build_ca`; use a Compose build override with `secrets: [build_ca]` and a host CA bundle. Pass `--build-arg HTTPS_PROXY --build-arg HTTP_PROXY --build-arg NO_PROXY`; never bake proxy credentials or disable certificate validation. Cloud-specific overrides belong outside the repository. The initial cloud build was blocked by the Google storage redirect allowlist; after network changes, API/web/storage builds and the full local stack passed. Ensure sufficient disk for the source build and reclaim only unused build caches when necessary; do not delete data volumes.
