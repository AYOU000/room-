# Room, Timer, and Media Contracts

**Status:** Draft v0.1  
**Date:** 7 November 2026  
**Owners:** Member 2 (implementation), Member 1 (data/auth review), Member 5 (security review)  
**Basis:** ROOM Software Requirements Specification v1.0 and Team Roles and Responsibilities v1.0

This document turns the SRS requirements for room admission, debate lifecycle, timers, reconnects, real-time events, and LiveKit access into contracts that Members 1–5 can implement against. Values described as **proposed defaults** come from the SRS and remain changeable by team agreement.

## 1. Contract principles

1. The API is authoritative for identity, membership, consent, state, start/end timestamps, disconnect deadlines, and media grants.
2. A client may request a transition; it cannot directly set a state, remaining time, participant identity, room name, or end reason.
3. PostgreSQL stores durable room/session state and timing metadata. Raw audio and transcript text remain ephemeral and are outside these contracts.
4. All mutations are authenticated, membership-checked, validated at the server boundary, and safe to retry.
5. The user-facing application has exactly two human participant slots. An authorized ASR service identity is not a human participant and does not consume a slot.
6. One session is one timed audio discussion. No debate phases, video, screen sharing, or audience are implied.

## 2. Identifiers, actors, and durable state

- `roomId`, `sessionId`, and `participantId` are UUIDs in application APIs.
- The authenticated account is derived from the verified access token. Request bodies never choose the acting user.
- A room has one creator and at most one invited second human. Membership is unique per account and room.
- A session has a fixed topic snapshot, configured duration, start/end timestamps, and two participant slots.
- LiveKit room names are generated by the server from the session ID (for example, `room_<sessionId>`). They are not accepted from a production client.
- Persisted session states are `waiting | active | finishing | ended | cancelled`. Evaluation is separate: `pending | processing | completed | failed | unavailable`.
- End reasons are `timer | user_end | disconnect | service_failure`. Cancellation is represented by the terminal state `cancelled`, with a separate cancellation reason if the product needs one.

The database must enforce unique `(session_id, participant_id)` and `(session_id, slot)`, with slot restricted to 1 or 2. Admission of a second participant and assignment of their slot must be one transaction. A third or duplicate join cannot create another slot.

## 3. State and transition contract

| Current state | Request/event | Preconditions | Result |
|---|---|---|---|
| waiting | creator edits topic or duration | Creator; room has not started | Updated waiting state; clear both readiness acknowledgements |
| waiting | participant becomes ready | Member; current consent version accepted | Readiness updated; state remains waiting |
| waiting | creator starts | Both human members joined, consented, ready, and have usable audio connections | Atomically set `active`, `startedAt`, and `endsAt` |
| waiting | creator leaves or room expires | Room is still waiting | `cancelled`; release both slots |
| active | either participant ends | Authenticated member; explicit UI confirmation precedes request | Atomically set `finishing`; end reason `user_end` |
| active | authoritative deadline reached | Server clock reaches `endsAt` | Atomically set `finishing`; end reason `timer` |
| active | participant disconnect grace expires | No successful reconnect before that participant's deadline | Atomically set `finishing`; end reason `disconnect` |
| active | unrecoverable service failure | Failure policy determines the session cannot continue | Atomically set `finishing`; end reason `service_failure` |
| finishing | media stopped and finalization completed or bounded drain expires | Finalization owner closes capture and freezes permitted transient snapshot | `ended`; evaluation proceeds independently |
| ended / cancelled | any start, ready, or finish mutation | Terminal state | No transition; return current representation |

Room/session state changes are serialized in a database transaction or equivalent compare-and-set. The winning transition sets `endedAt` once. Competing timer, user-finish, disconnect, and service-failure triggers must not create multiple terminal events or duplicate evaluation work.

### Idempotency

- Repeating a successful start request returns the current active/terminal representation and never resets `startedAt` or `endsAt`.
- Repeating finish after the session has entered `finishing` or `ended` returns the same `sessionId`, state, end reason, and evaluation status. It does not enqueue another evaluation.
- A request that is valid for a member but conflicts with a transition already won by another event returns the latest state with HTTP 200 for idempotent start/finish, or HTTP 409 for a distinct invalid mutation such as editing an active room.
- If an `Idempotency-Key` header is used for create/join, scope it to the authenticated account and operation; key reuse with a different request body returns `409 IDEMPOTENCY_KEY_REUSED`.

## 4. HTTP API

The repository currently uses the `/api` prefix for its media-token route; the proposed routes below use that prefix consistently. All JSON mutation routes require `Content-Type: application/json`, strict request schemas, the authenticated principal, and the configured Origin/CSRF protections.

### Create and inspect

#### `POST /api/rooms`

Creator creates a waiting room and its waiting session.

Request:
```json
{
  "title": "Should universities require community service?",
  "description": "Optional topic context",
  "durationSeconds": 600
}
```

Validation: title 5–200 characters; optional description at most 2,000 characters; duration 120–1,800 seconds, default 600. Response `201` contains the authorized room/session summary and an invite code only for the creator. Store only a hash of the invite code. Proposed invite expiry: 24 hours or room closure, whichever comes first.

#### `POST /api/rooms/join`

Request:
```json
{ "inviteCode": "..." }
```

The server validates expiry and capacity, then atomically admits the authenticated account. A user cannot join their own room as the second member. An expired, invalid, or full invite is rejected without revealing unnecessary room details.

#### `GET /api/rooms/:roomId`

Returns a membership-gated snapshot:

```json
{
  "room": {
    "id": "uuid",
    "status": "waiting",
    "creatorId": "uuid",
    "title": "Debate topic",
    "durationSeconds": 600
  },
  "session": {
    "id": "uuid",
    "state": "waiting",
    "evaluationStatus": "pending",
    "startedAt": null,
    "endsAt": null,
    "serverTime": "2026-11-07T09:00:00.000Z",
    "endReason": null
  },
  "participants": [
    { "participantId": "uuid", "slot": 1, "ready": false, "connection": "disconnected" }
  ]
}
```

Only members see participant/account information. Do not return invite hashes, media credentials, secrets, or another user's private history.

### Waiting-room mutations

#### `PATCH /api/rooms/:roomId`

Creator-only; waiting state only. Accepts the same validated topic/duration fields. A successful change clears readiness for both participants and emits a new room-state event. Unknown fields are rejected.

#### `POST /api/rooms/:roomId/ready`

Request:
```json
{ "consentVersion": "privacy-v1", "ready": true }
```

The server records consent and readiness for the authenticated participant. Readiness may be withdrawn while waiting. Editing the topic/duration, changing the consent notice version, or leaving resets relevant acknowledgements. Both participants must acknowledge the current consent version.

#### `POST /api/rooms/:roomId/start`

Creator-only. Requires both participants to have current consent, be ready, and have a usable audio connection. The server sets `startedAt = now` and `endsAt = startedAt + durationSeconds` in one atomic transition. Response is the active session snapshot with authoritative timestamps.

### Media token

#### `POST /api/sessions/:sessionId/media-token`

Authenticated session member only. The production request body is empty; server resolves the LiveKit room and identity from the authenticated account and session membership. This is intentionally different from the current development token path, which accepts `roomName` and `identity` in the request.

A member who has accepted the current consent notice may receive a waiting-room token for audio preflight with `canPublish: false` and intended subscriptions only. After the session becomes active, the member requests a fresh token with microphone-only publish permission. Active-session renewal is allowed only while membership and active state remain valid. No token is issued for cancelled or ended sessions.

Response:
```json
{
  "sessionId": "uuid",
  "roomName": "room_<server-generated-session-id>",
  "participantId": "uuid",
  "token": "<short-lived LiveKit JWT>",
  "serverUrl": "wss://media.example"
}
```

Proposed token lifetime: five minutes. Every issuance or renewal rechecks membership, consent, and state-specific grants; it cannot reopen a terminal session. The LiveKit token is returned only to the authenticated participant and must never be logged, persisted in localStorage, or included in analytics.

### Finish

#### `POST /api/sessions/:sessionId/finish`

Authenticated member only. Client cannot set `endReason`, `endedAt`, or evaluation status. The server chooses `user_end` and enters `finishing` only if the session is active. UI confirmation is required before calling this route.

Response:
```json
{
  "sessionId": "uuid",
  "state": "finishing",
  "endReason": "user_end",
  "endedAt": "2026-11-07T09:05:00.000Z",
  "evaluationStatus": "pending"
}
```

The same response shape returns the current values on retry. Timer and disconnect handlers use the same internal transition operation, not a client-callable end-reason parameter.

### Stable error envelope

All API errors use the shared error handler and include a request ID:

```json
{
  "error": {
    "code": "ROOM_FULL",
    "message": "This room is full.",
    "requestId": "..."
  }
}
```

Proposed status mapping: `400 INVALID_INPUT`, `401 UNAUTHENTICATED`, `403 FORBIDDEN`, non-disclosing `404 NOT_FOUND`, `409 ROOM_FULL | INVALID_STATE | NOT_READY | AUDIO_NOT_CONNECTED`, `413 PAYLOAD_TOO_LARGE`, `429 RATE_LIMITED`, and `503 SERVICE_UNAVAILABLE`. Never return stack traces or internal provider detail.

## 5. Authoritative timer contract

- `startedAt` and `endsAt` are server-generated UTC instants stored with the session. Duration is fixed once the session starts.
- Server time is the source of truth. The browser displays a countdown from `endsAt - estimatedServerNow`; it does not decrement a client-owned timer as authority.
- Every room snapshot/event includes `serverTime`. The UI estimates server offset using request/response timing and a monotonic browser clock. Local wall-clock changes must not extend the session.
- The displayed remaining value is `max(0, endsAt - estimatedServerNow)`. At zero, the client shows expiry and waits for the server's terminal transition; it never decides the official end reason.
- Timer expiry is enforced server-side, including after a process restart. An in-memory timer may wake the transition promptly, but durable `endsAt` is authoritative. Startup reconciliation and a periodic due-session sweep must finish active rows whose deadline has passed.
- Timer expiry and finish requests race through the same atomic state transition. The first valid transition wins. Retries and duplicate timer jobs are harmless.
- On reconnect, the client fetches a fresh room/session snapshot and resynchronizes from `serverTime` and `endsAt`. It never restores a cached remaining duration.

## 6. Disconnect and reconnect contract

- Proposed disconnect grace: 60 seconds per human participant. Media disconnection does not pause or reset debate time.
- A verified LiveKit participant-disconnected event starts that participant's server-side grace deadline. Webhook signatures must be verified and event IDs deduplicated. If the implementation uses server SDK callbacks instead, they must carry equivalent authenticated room/identity data.
- A successful reconnect by the same authorized account before the deadline clears that participant's pending grace deadline. It does not reset `startedAt` or `endsAt`.
- If grace expires while the session is active, the session transitions to `finishing` with `disconnect`. A later reconnect cannot revive it; the client gets the terminal snapshot.
- Unknown identities, stale events, duplicate events, and events for another LiveKit room do not change state.
- Network loss does not release a slot or admit a third person. Creator departure while waiting cancels the room; creator disconnection after start follows the same grace policy as any other participant.

## 7. Live event contract

Transport: authenticated WebSocket at `/api/events`. Validate the browser Origin, authenticate the connection, and authorize every requested session subscription. Only session members may subscribe. Enforce frame limits (16 KiB maximum), rate limits, schema validation, and ping/pong timeouts. Client-sent frames are limited to subscription/acknowledgement and heartbeat; lifecycle mutations use HTTP routes.

Every server event has this envelope:

```json
{
  "eventId": "uuid",
  "sessionId": "uuid",
  "type": "timer.sync",
  "sequence": 17,
  "serverTime": "2026-11-07T09:00:05.000Z",
  "payload": {
    "state": "active",
    "startedAt": "2026-11-07T09:00:00.000Z",
    "endsAt": "2026-11-07T09:10:00.000Z"
  }
}
```

- `sequence` is monotonically increasing within a session. Repeated delivery with the same `eventId` or sequence is ignored.
- A gap causes the client to fetch `GET /api/rooms/:roomId` and reconcile. On reconnect, always fetch the snapshot first. A transcript snapshot may be requested only while active and is served from the authorized server-memory buffer.
- Relevant event types: `room.updated`, `participant.updated`, `session.state`, `timer.sync`, `media.participant`, `transcript.segment`, and `evaluation.status`. Transcript payload ownership and schema remain defined by the separate transcription contract.
- Terminal `session.state` stops further transcript event delivery. The event stream contains no access token, refresh token, invite code, raw audio, or secrets.
- Clients must tolerate delayed, duplicated, or out-of-order delivery and converge to the latest authorized snapshot.

## 8. LiveKit media policy

### Human participant grant

A server-issued LiveKit grant for a human participant is bound to the session-derived room name and server-derived identity. In the waiting state, it permits joining and intended subscriptions for audio preflight, but has `canPublish: false`. Once the session is active, a newly issued grant permits:

- joining that one room;
- publishing microphone audio only (`canPublishSources: [MICROPHONE]`);
- subscribing to intended audio tracks.

Both grant types deny camera/screen publication, data publication, room administration, recording, and metadata updates. The client cannot choose the grant's room or identity. Permission to use the browser microphone is separately requested by the browser and does not itself authorize room membership.

### ASR service grant

The transcription service is a separate, server-authenticated identity. It is not counted as one of the two human slots. Its credentials are never sent to browsers. It may join only the session room it is authorized to process and subscribe to the two human microphone tracks. It cannot publish, send data, administer, record, or update metadata unless a later reviewed contract explicitly changes that scope.

Official speaker identity is resolved from the authenticated LiveKit track owner, not from client labels or ASR diarization. Unknown or ambiguous ownership remains unknown; it is never guessed.

### Mute, renewal, and shutdown

- Mute/unmute controls operate on the participant's local microphone track. UI state reflects the actual local track and, where available, server-observed publication state.
- Token expiry is not a media shutdown mechanism; an already connected participant may remain connected.
- When the session enters `finishing`, the backend stops accepting new grants, removes/updates human participants to revoke active media, stops ASR capture, drains final transcript output for at most five seconds, and closes the LiveKit room. It then freezes the permitted evaluation snapshot and transitions to `ended`.
- Cleanup is idempotent and retried on transient LiveKit failure. Session state still becomes terminal; a cleanup failure is recorded as a redacted operational error and cannot reopen the session.
- Do not persist or log audio, transcript text, LiveKit JWTs, raw webhook bodies, or provider payloads.

## 10. Acceptance checks

1. Two concurrent join requests for the last slot admit exactly one account; a third human is rejected.
2. A nonmember and a guessed session ID cannot read state or mint a media grant.
3. A client-supplied identity/room cannot affect a production media grant.
4. Start fails until both members have accepted current consent, are ready, and have connected audio; only the creator can start.
5. Changing the browser wall clock and reloading cannot extend the timer; reconnect returns the original `startedAt` and `endsAt`.
6. Concurrent user finish, timer expiry, and duplicate webhook delivery produce one terminal transition and one evaluation trigger.
7. A reconnect within 60 seconds restores current state without pausing or resetting the timer; grace expiry ends the session and later reconnect is rejected.
8. Camera, screen, data publication, administration, and recording grants are denied; the ASR identity can subscribe only to its authorized session.
9. Finishing removes active media participants and closes the room even when the access token has not expired.
10. Restart reconciliation ends overdue sessions and marks evaluation unavailable if the ephemeral transcript buffer no longer exists.
11. Logs and persistent storage contain no raw transcript, audio, invite secret, or media JWT.
